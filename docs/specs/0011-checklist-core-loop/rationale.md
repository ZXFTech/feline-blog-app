# 0011. 确认清单核心闭环：决策理由

## Context

仓库已经有完整的清单卡片、清单项卡片、清单表单、日历和 Dialog 交互，但它们目前主要服务于组件迁移和展示，没有正式页面、账号数据和 PostgreSQL 闭环。本次目标不是重新设计清单，而是把既有设计系统接入一个可以每天使用的私人工作流。

经过设计讨论，范围增加了搜索、无限滚动、虚拟列表、批量删除、回收站和三十天恢复，同时明确排除了提醒与分享。这些能力仍围绕同一个核心生命周期：创建，确认，查找，编辑，删除，恢复和到期清理。

实际使用进一步暴露了三个交互问题。长按查看详情不易发现，也会和点击切换状态竞争。把多个独立动作合并成按钮组则让删除、编辑和查看详情看起来像一个分段选择器，偏离项目现有组件语义；互斥筛选本身仍适合用按钮组表达。固定四列和两列断点还会让卡片在临界宽度突然跳变，并浪费减列后的可用行宽。

## Rationale

选择独立页面、服务端领域服务、PostgreSQL 持久化、现有组件扩展、`react-virtuoso` 虚拟化和 Vercel Cron 清理。

这个方案让首个实现切片就能从页面到权限、数据和真实交互完整打通。服务端组件负责首屏，Server Action 负责有状态写入，Route Handler 只承担滚动分页和 Cron 这两类 HTTP 边界。所有数据库调用留在服务端并按所有者过滤。

现有 `react-virtuoso` 已覆盖响应式网格、虚拟列表和结束加载，不需要再引入 TanStack Virtual。卡片只增加显式布局变体，避免复制视觉组件。Vercel Cron 与当前部署平台一致，并通过应用 Route Handler 使用同一套数据库和安全边界，避免为清理任务建立第二套 Supabase 调度配置。

清单项卡片采用显式详情、编辑和删除按钮，详情文本区单独承担状态切换。表单编辑仍属于父级聚合草稿，详情页没有未保存的父级表单，因此允许用同一个编辑 Dialog 立即持久化单项。两种保存边界都复用同一字段规则，但不会混用事务语义。

项目卡片网格根据容器宽度、根字号、项目数量和固定 gap 决定列数，保持 12rem 至 12.5rem 正方形；达到上限后的余白放在轨道组两侧。这替代早期 auto-fit / 1fr 铺满方案，符合用户后续确认的最大尺寸和居中要求。异常窄嵌入仍只让网格包装层局部横向滚动。

## Options considered

### 单页和弹窗完成全部流程

优点是路由少，初期看似更快。缺点是创建、编辑、搜索、筛选、批量管理和回收站会拥挤在同一个客户端状态树中，深链接和刷新恢复也更弱。用户已经确认独立页面，因此不采用。

### 新建清单视觉组件和新的虚拟列表依赖

优点是可以从零定制。缺点是重复现有卡片、表单、Dialog、token 和 `react-virtuoso`，会造成样式漂移并违反不自行设计的边界。用户确认扩展现有卡片并复用现有依赖，因此不采用。

### 仅浏览器本地持久化

优点是没有数据库迁移，原型速度最快。缺点是无法提供账号所有权、跨设备数据、可靠回收站、并发控制和服务端清理，不满足正式核心闭环，因此不采用。

### Supabase Cron 清理

Supabase Cron 可以直接在数据库中调度 SQL 或函数，适合纯数据库任务。这里选择 Vercel Cron，因为应用的本地、测试和暂存环境已经以同一套服务端领域边界访问 PostgreSQL。清理逻辑保留在应用层更容易复用鉴权、日志、批次和测试约定。代价是需要保护一个 HTTP 路由和配置 `CRON_SECRET`。

### 硬删除

硬删除查询简单，但不能满足所有删除都可在三十天内恢复的确认要求。软删除会增加索引和恢复路径复杂度，因此本规格用部分索引、固定恢复窗口和每日物理清理控制成本。

### 每点击一次“添加清单项”就追加一个空白表单

优点是所有输入同时可见。缺点是用户很难区分空白占位和已经添加的事项，删除按钮同时承担“丢弃空表单”和“删除业务项”两种语义，并且大量字段会让页面变长、验证与焦点定位更复杂。因此改为一个固定新增器，成功添加后用卡片表达已进入聚合草稿的项目。

### 在编辑页立即持久化卡片编辑和删除

优点是单项操作立即生效并立刻出现在回收站。缺点是每次子项写入都会递增父级 revision，与仍未保存的父表单制造自冲突；取消整份编辑也无法自然撤销已经提交的子项写入。除非把整个编辑页改造成全字段自动保存，否则这是一种失败边界不一致的混合模型，因此不采用。

### 整张卡片切换状态并用长按查看详情

优点是卡片任意位置都容易点中，并且少一个可见按钮。缺点是长按入口难以发现，也容易在触控设备上与状态切换、滚动和卡片内操作冲突。采用详情文本区切换状态和右上显式详情按钮，让查看、编辑、删除和确认各自有稳定目标。

### 非筛选操作继续使用按钮组

优点是按钮能紧密排列。缺点是按钮组表达的是同一组互斥选项或连续控制，而删除、编辑、详情和保存是独立动作。搜索栏筛选和详情页的全部、已完成、未完成筛选保留 `ButtonGroup`；其他动作使用共享 `Button` 或 `StyledLink` 并按间距 token 排列。

### 固定四列和两列断点

优点是列数容易预测，既有 1087 和 1088 像素断言也直接。缺点是卡片不能在当前列数内自然吸收宽度，临界点会跨两列跳变，移动端仍被固定为两列，并且每次调整最小卡片尺寸都要重算断点。因此用项目网格自身宽度、最小轨道和 gap 自然决定列数。

### 无最大尺寸并铺满行宽（已被后续决定替代）

早期 1fr 方案使少量项目显著放大。用户后续明确最大宽高 12.5rem、固定间距和整体居中，因此当前采用有上限轨道，接受两侧留白。不完整末行仍对齐已有轨道，不单独拉伸或逐行居中。

### 为所有清单项提供一个全局项目回收站页面

优点是可以集中浏览全部已删除项目。缺点是清单项脱离父清单后缺少上下文，恢复时仍必须校验并刷新所属父级，也会让 `/checklists/trash` 同时承担两类层级不同的恢复流程。项目恢复因此收进所属清单详情的 Dialog；清单级回收站只恢复父清单，父级被删时先恢复父级再管理其项目。

### 保存时自动把新增器中的半成品当作清单项

优点是少一次点击。缺点是用户没有明确执行“添加”，无效内容也会改变父级提交含义，并且与“已添加卡片列表就是最终载荷”的心智模型冲突。因此保存前只提示存在未添加内容；继续明确丢弃它，取消则回到新增器处理。

## Key tradeoffs

必填截止时间提高了每次创建的输入成本，但它提供了清晰的最近到期排序和过期视图，是防遗漏目标的核心信号。

状态和计数实时派生避免缓存列漂移，但查询必须同时考虑有效子项。相应索引和 24 条批次限制把成本控制在可验证范围内。

无限滚动采用冻结过期判断时刻的实时 keyset，而不声称拥有跨 HTTP 请求的数据库快照。这样不需要维护昂贵的集合快照；代价是其他会话在分页期间修改排序或筛选字段时可能暂时遗漏，下一次首批刷新会纠正。

搜索从 1 个字符开始符合直接反馈预期，但极短搜索可能不能充分利用 trigram 索引。保留正确性，接受短查询效率较低，并通过防抖、批次和结果虚拟化限制负载。

软删除父级而不同时改写所有子项保存了子项原有删除语义。恢复父级后，原本有效的子项自动回来，之前单独删除的子项仍在其恢复窗口内，规则可解释且不需要级联更新时间戳。

创建和编辑表面采用“一个固定新增器 + 一个卡片草稿列表”，而不是继续用可增长的内联表单数组。用户的主要动作是连续录入独立事项；固定新增器在每次成功添加后复位，减少页面纵向跳动，也把“正在输入但尚未加入”和“已经会随清单保存”区分开。新增器与编辑 Dialog 共享字段组件但不共享实例状态，避免取消编辑时意外覆盖新增器中的半成品。

清单项只保留一个必填详情字段，并允许重复内容。这里的事项是可独立确认的文本，而不是具有标题和正文层级的文档；双字段会增加录入成本，却没有对应的展示或查询价值。重复文本不能充当身份，所有编辑、删除、恢复和焦点定位都继续使用稳定 ID 或客户端草稿键。

该清单功能尚未发布，现有清单项目数据只在明确允许的本地或暂存环境中视为可丢弃开发数据。部署迁移本身不承担删除职责，而是在发现旧清单行时写入前停止；清理必须由操作者对允许名单中的目标显式运行 reset 工具。已经在共享环境应用的迁移保持不可变，模型修正使用前向迁移。这样避免误删保留数据和迁移历史漂移；代价是带旧数据的环境必须先由人工确认处置，不能自动升级。

已删除项目 Dialog 不提供搜索。单个清单最多 200 个项目，按删除时间分页已经足够；只搜索已加载行会制造结果完整性的错觉，而为这一个 Dialog增加另一套服务端搜索和游标签名不值得本轮复杂度。

既有项在编辑页删除时选择随清单保存统一提交，而不是立即调用单项软删除。即时删除看似反馈更直接，但它会先递增父级 revision，使同一页面剩余未保存的清单名称、截止时间和其他项目编辑立即变成陈旧草稿，还会产生“删除已生效但点击取消编辑无法恢复”的混合语义。聚合提交保留现有原子编辑契约：确认删除只改变本地 diff，保存成功才进入所属清单的已删除项目集合并提供撤销；未保存新项则永远只存在于浏览器，不应制造虚假的恢复记录。

详情页没有聚合草稿，因此单项编辑可以立即提交。它仍锁定父级并校验父子 revision，成功后同时递增两者，保证另一标签页里较早打开的聚合编辑不会静默覆盖这次修改。代价是并发编辑更容易显式出现冲突，但这是保护数据而不是隐藏冲突的正确行为。

保存时若新增器仍有原始输入，先确认而不自动追加。这个边界让“已添加卡片列表”始终等于提交载荷，也避免用户误以为只是保存清单元数据却悄悄创建了一个项目。请求在途期间冻结整个草稿，确保服务端字段错误、revision 和成功响应都对应同一份提交快照。

项目网格的减列阈值由最小轨道和固定 `gap-3` 共同决定，而不是由 viewport 或页面级断点决定。固定 gap 避免缩窄过程中因间距切换出现列数反向增加。实际活动列数还受项目数量限制。这样嵌套容器、祖先 padding 和根字号变化都由浏览器布局计算自然处理。代价是具体列数不再对应一个固定像素表，验证必须用足量项目测量网格 content box、卡片实际尺寸和阈值两侧行为。

恢复资格在三十天边界实时失效，但物理删除只能是正常调度下的 24 小时目标。把它表述为目标而不是保证，避免一次 Cron 失败造成无法兑现的业务承诺，同时不延长用户可恢复窗口。

## 2026-09-23 交互修订理由

本次选择原地修复。详情页把编辑、删除纳入现有批量管理入口，减少正常确认时的操作干扰；表单没有批量入口，按用户澄清保留两个按钮常显。隐藏动作保留空操作槽，以避免切换模式时正文或卡片尺寸跳动。

截图中的白色时间列表由浏览器原生 type=time 控件提供。仅修改输入框外观无法给系统列表提供项目的四套主题。用户选择以现有 Select 组合小时和分钟，保留原分钟精度与 localDateTime 保存边界；相比直接输入 HH:mm，代价是需要两个选择操作和嵌套浮层键盘回归，但复用现有组件可避免自建列表框的焦点与可访问性成本。维持原生控件虽能保留系统输入体验，却不能满足明确的主题要求；引入新时间库也没有足够收益。

表单各组保持纵排，组内标题与控件横排，添加按钮独立一行。其代价是短视口里的项目列表更矮，不能再通过把元数据改成三列来优化。保留 default 内边距，常规高度仅列表滚动。用户在另一模型审阅后批准短屏例外：不足完整一行卡片及列表内边距时，允许表单内部整体滚动，页面仍不滚。阈值取实际固定内容高度和卡片尺寸，避免任意设备断点或把几像素列表视为可用；验收覆盖内容高度、焦点可达性与阴影边界。

本轮不新增数据库迁移、后台任务、服务端接口、依赖或配置。可按界面组件回退实现，数据协议不受影响。本节记录新决定，不修改此前运行记录的历史事实。

详情页完成状态筛选采用当前会话中的派生展示状态。单个清单最多 200 个有效项目，详情页已经加载完整集合，因此没有必要增加 URL 契约、服务端筛选或新的分页边界。筛选组放在新增入口之前，帮助用户先缩小当前视图再执行项目操作。切换筛选会清空批量选择，避免不可见项目仍被后续批量动作处理；汇总计数继续描述整份清单，不随临时视图改变。

交叉审阅指出，筛选规则还必须覆盖详情页即时新增、项目批量删除、乐观状态和焦点恢复。保留现有详情页能力，并把它们正式纳入规格。详情新增使用浏览器项目 UUID 作为一次意图的稳定重试身份，持久化时间、顺序、revision 和确认状态仍由服务端事务决定。相比结果未知后生成新 ID，这能安全辨认首次写入并避免重复项目。

详情页批量删除与清单列表批量删除分开定义。它只处理当前筛选下明确选择的项目，在一个父级事务中校验所有 revisions 和最后一项不变量，并把成功响应中的精确目标交给统一恢复动作。筛选值变化清空全部选择，数据重读只移除已经不可见的 ID，这同时避免隐藏目标被误删，也不会因无关的权威刷新丢掉仍安全的选择。

筛选和乐观确认使用布尔 `effectiveCompletion`，不伪造客户端 `confirmedAt`。数据库时间继续是确认时间的唯一来源。可见项目数量只负责网格列数和空状态，整份清单计数继续来自完整有效集合。这样能让筛选后的居中网格符合当前视图，同时不改变汇总语义。卡片因状态变化移出当前结果时按相邻卡片到筛选按钮恢复焦点，防止键盘焦点随节点消失。

另一模型指出 Radix Select 与 Base UI Popover 默认 Portal 不共享交互边界。采用局部 Portal 容器适配与真实交互验收；日期弹层和选项列表分别按可见视口限高滚动。本轮修正只更新设计和待执行验收，不将历史测试结果当作新规则通过证据。
