# Rationale: 0001 · 番茄钟记录幂等与离线完成

## Context

现有番茄钟使用 React reducer 管理状态，使用 `localStorage` 恢复计时，并在阶段切换时由插件直接调用 Server Action 创建历史。插件运行环境会随状态变化重建，客户端也没有稳定事件标识。刷新、React 重复执行、请求重试和多标签页因此可能重复写入。

当前恢复流程还不能可靠表达页面关闭期间已经结束的阶段。计时状态和历史结果分别保存时，浏览器也可能在两次写入之间关闭，造成结果丢失或重复。

这是登录用户的私人效率数据。它不涉及新的合规范围，也不需要新的基础设施。设计需要沿用现有 Next.js、Prisma、MariaDB、自定义 JWT 和插件结构，并兼容旧历史记录。

## Options considered

### Option 1: 扩展现有记录并使用本地待同步队列

给现有 `PomodoroRecord` 增加事件标识和结束原因。浏览器按用户保存计时状态，并按事件保存独立待同步项。服务端通过组合唯一约束完成幂等写入。

**Pros**:

1. 保留现有页面、插件、数据库关系和历史查询。
2. 无需新服务或新依赖。
3. 数据库约束可以处理真正的并发重复请求。

**Cons**:

1. 客户端需要管理队列、版本迁移和错误状态。
2. 旧记录的新字段需要保持为空，读取代码必须兼容。

### Option 2: 新增番茄会话实体

新增会话实体表示一个完整循环，阶段记录挂在会话下。它能支持跨阶段分析和未来任务关联。

**Pros**:

1. 完整循环有明确领域身份。
2. 后续扩展跨阶段统计更自然。

**Cons**:

1. 本次只需要阶段结果，新增会话会扩大迁移和界面范围。
2. 仍然需要阶段级事件标识和客户端恢复规则。

### Option 3: 新增独立幂等请求表

保留历史表不变，用另一张表记录已经处理的事件标识和请求摘要。

**Pros**:

1. 幂等机制可以扩展给其他写入操作。
2. 历史表结构变化较少。

**Cons**:

1. 多一张表、一次事务和清理策略。
2. 当前项目没有其他需要共享该机制的写入场景。

## Rationale

问题的核心是阶段结果缺少稳定身份，以及本地状态与写入结果之间存在持久化空隙，不是缺少新的会话领域模型。扩展现有表可以用最小改动把客户端恢复、服务端写入和历史展示贯通。

数据库唯一约束是最终裁决者。仅在客户端去重无法覆盖多标签页和并发请求。独立幂等表可以工作，但会增加本项目目前不需要的通用基础设施。
