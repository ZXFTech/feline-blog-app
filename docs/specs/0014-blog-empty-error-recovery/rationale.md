# Rationale: Blog 空状态与错误恢复修复

构建规格见 [index.md](index.md)。以下保留原规格的决策背景。

## Context

scope 31 承接 Blog P2 的状态修复。当前列表没有页面标题、结果说明或空态；详情把不存在的文章呈现为猫图空态，并在服务端调用消息提示。相邻导航只有 loading 和空邻居值，读取失败后会显示已经到达首尾，无法区分成功与失败。

`/blog` 没有专属 loading 或 error 文件。新建和编辑页目前继承全站转圈及框架默认错误界面；编辑页已有的读取失败分支会跳回文章列表。搜索输入未从 URL 回显，500ms 防抖没有撤销机制，清除搜索后可能被旧回调重新写回。

这是现有 Web 功能的 ENHANCEMENT，按 Tracer Bullet 逐条打通真实阅读路径，沿用 Beta 验证流程。你已确认文字 404、手动重试、清除搜索保留排序、空正文的准确文案，以及整个 `/blog` 的中文兜底范围。不新增业务实体或数据库字段，不重做文章发现、编辑器或全站布局。

## Options considered

### Option 1: 在现有入口内补齐状态与恢复

保留现有路由、查询和正文组件，新增 Blog 局部展示与恢复边界，按列表、详情、相邻导航分别接入。

**Pros**: 改动集中，可以逐条验证真实流程，不新增部署或数据维护成本。

**Cons**: 页面刷新重试与相邻导航局部重试需要各自实现并遵守同一反馈约定，共用兜底也影响作者页的加载和意外错误呈现。

### Option 2: 新旧状态方案并行，逐步切换

建立独立阅读入口和状态适配层，保留原入口，通过开关逐页迁入。

**Pros**: 适合大量页面迁移，可以按入口独立回退。

**Cons**: 本轮三个读取入口不足以抵消重复路由、适配和配置的成本，旧错误分支仍需同时维护。

### Option 3: 直接替换 Blog 数据加载与页面结构

整体重建 Blog 的客户端查询、缓存和错误处理，再重新接入阅读及作者页面。

**Pros**: 加载和重试可集中在统一的数据层。

**Cons**: 扩大正文输出、缓存、权限和作者流程的回归范围，超出状态修复的边界。

## Rationale

根因是成功、空值与失败被混用，以及缺少与状态对应的恢复操作。现有 `ActionResult` 已提供区分依据，不需要引入另一套数据请求系统。原地修复能保留已完成的正文和阅读控制器，也能先交付一次真实查询失败后恢复的完整路径。

你选择共用整个 `/blog` 的加载与崩溃提示，因此无需为隔离作者页而移动路由。保留“正文为空”的正常详情身份，使文章信息和已有互动仍然有效。文章不存在时无法取得可靠主题和标签，且当前没有关联推荐查询，暂缓推荐可以保持本轮恢复行为的范围清晰。

## 2026-10-23 恢复方式修订

此前审查在 Next 16.3.3 的真实路由中确认，同 pathname 的 `router.refresh()` 虽能取得恢复后的文章，仍保留已触发的缺页状态；错误列表通过客户端链接返回同 pathname，也会保留旧错误边界。仅有新数据或目标 href 正确不足以完成恢复。

本次把已实现、复验并经独立模型审查通过的方式同步为规格：404 重查用 `window.location.reload()` 完整刷新当前地址；`BlogRecovery` 的返回入口用固定 `/blog` 原生链接完整导航。这样无需依赖框架内部清除接口，仍保留真实链接语义与共享样式。普通预期读取失败继续使用 `router.refresh()`，路由错误重试继续使用框架 `retry()`，相邻导航保持局部重试。

接受的代价是这两种文档导航会重建页面，焦点、滚动恢复和片段定位遵循浏览器行为，可能从 BODY 开始，不承诺保留旧控件、旧滚动位置或内存草稿。只有不更换文档的重试继续执行条件聚焦与 `preventScroll`，用户已移走焦点时不抢回。
