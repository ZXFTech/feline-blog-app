# 0015. Blog 容器间距与窄屏布局修复

**Date**: 2026-10-23
**Status**: Proposed

## Summary

在现有 Blog 页面内收口容器间距、长内容换行和滚动边界。从 320 CSS 像素开始验证，保留默认内边距，用换行和堆叠安排窄屏内容。先在真实页面记录问题，再逐段修复，继续复用现有正文、目录和状态规则。

## Context

本规格对应 `docs/scope/scope.md` 第 32 项，属于现有 Web 应用的 ENHANCEMENT。设计来源是现有 `design.md`、共享组件与当前界面。0012 定义正文与代码块，0013 定义目录与阅读进度，0014 定义空状态与错误恢复，本规格补充它们之间的容器布局契约。

当前工作区包含 0014 的未提交实现，设计以这些文件为基线。源码侦察只发现待验证点：列表标签行没有换行设置，Tag 内层文字默认不换行，列表集合、卡片、阅读操作区和相邻导航分别添加外边距。这里没有浏览器复现结果，不将这些写成已证实的用户故障。

范围覆盖公开列表、详情、桌面与窄屏目录、阅读操作区、相邻导航及加载、空白、失败、404 界面。共享 Blog 兜底用于新建和编辑页时一并检查其布局，编辑器正常页面仍由 scope 第 33 项承接。阅读操作含义由 scope 第 29 项承接，文章发现、SEO 和全站容器迁移各自保留原范围。

## Requirements

**User stories**:

1. 作为读者，我希望在窄窗口完整阅读标题、标签和正文，并能到达全部现有操作。
2. 作为键盘用户，我希望长内容仍可滚动，焦点和内部阴影不被容器边界裁切。
3. 作为维护者，我希望面板内外间距有明确归属，修复依据可以在真实页面重复核验。

**Acceptance criteria**:

1. **AC-1**: 修复前记录真实 `/blog` 和 `/blog/[id]` 的基线，包含页面、内容样例、视口、主题、实际容器宽度和滚动根。每个待修点都有复现证据，或明确的未复现记录与排除依据，不用源码猜测代替运行观察。
2. **AC-2**: 内容容器默认使用 default 内边距。其他密度和零内边距在调用处显式表达，间距表说明其用途和阴影留白归属。面板负责内部 padding 与直接子元素 gap，父布局负责相邻面板 gap，不叠加常规子元素 margin 来凑间距。0012 的正文与代码块间距例外继续有效。
3. **AC-3**: 从 320 CSS 像素到桌面，列表与详情的文章标题、作者、标签、搜索上下文和相邻文章标题完整显示。多标签自然换行，无空格长串也可断行，不增加截断、固定行数或额外展开入口，不通过删减内容适配宽度。
4. **AC-4**: 搜索、排序、清除、新建、编辑、阅读操作、目录开关及恢复操作在空间不足时换行或堆叠。现有可用操作可直接到达，键盘顺序连贯，焦点可见，不为节省宽度新增菜单或工具栏横滚，也不新增全局最小点击尺寸规则。
5. **AC-5**: 长代码和宽表格仅在各自区域横向滚动，键盘与触摸可操作，正文图片保持比例且不超过内容宽度。代码默认横滚及逐块换行沿用 0012。局部溢出不撑宽页面，不通过全局裁剪隐藏超宽内容。
6. **AC-6**: 主阅读区、侧栏及局部滚动区域保留必要内边距和可用高度。滚到开头、末尾时，内部控件阴影、焦点和最后一个操作仍可见；页面能滚到最后一个内容区域。滚动条默认隐藏，但滚动能力仍可使用。
7. **AC-7**: 沿用 Content 的 1088px 容器断点、现有主阅读栏最大宽度及桌面主区滚动、窄屏页面滚动规则。容器宽度为小数时也只显示一份活动目录，章节跳转、焦点与正文进度遵守 0013，不产生断点空隙或新的位置恢复机制。
8. **AC-8**: 加载、有内容、空列表、搜索无结果、空正文、读取失败、404、相邻导航加载与失败均遵守同一布局规则。等待和错误说明可换行，恢复按钮可达，切换状态后布局可自然增长，继续使用 0014 的文案、请求和恢复行为。
9. **AC-9**: 四主题 light、dark、sugar、warm、键盘和减少动态效果场景均可用。复用现有组件、token 和服务端内容输出，保持认证及 PostgreSQL 边界；共享组件如必须调整，另验证实际受影响的其他页面。
10. **AC-10**: 安全 Album 样例覆盖变更后的可视组件并维护注册表与来源覆盖。真实 Blog 页面验证、相关浏览器回归、Vitest、lint、类型检查和 build 有明确结果；需要账号的 Playwright 使用现有安全测试环境，缺少前置条件时明确标为未验证，不记为通过。

## Options considered

### Option 1: 在现有 Blog 内逐处修复

保留共享组件和阅读行为，在调用处与 Blog 样式中修复已确认问题。优点是影响范围小，现有实现可以逐段验证和回退；代价是需要逐层确认 padding、gap 与滚动归属。

### Option 2: 并行建立新的 Blog 布局壳

新旧壳并存，逐页切换。优点是可独立设计新布局；代价是暂时维护两套滚动和间距规则，目录实例、状态界面及展示样例都需要额外适配。

### Option 3: 直接重写共享 Content 与容器体系

统一处理全站布局。优点是可以一次清理历史差异；代价是影响清单、番茄钟、Album 等页面，验证范围远超过本轮 Blog 修复。

## Decision

**Chosen option**: Option 1，在现有 Blog 内逐处修复。

你已选择保留 default 内边距，标题和标签完整换行，操作区换行或堆叠。实现优先使用 Blog 调用处、静态可发现的 Tailwind 类及局部 CSS，由现有应用维护者随页面发布维护，无新增服务或依赖。

**Implementation skills**: `tailwind-css` (`paulrberg/agent-skills`, `.agents/skills/tailwind-css/`) · `typescript-react-patterns` (`asyrafhussin/agent-skills`, `.agents/skills/typescript-react-patterns/`)

内部实现建议保留列表卡片已有的显式 compact 密度，父级 gap 统一管理面板间距，阅读操作区保留普通容器。备选是将卡片统一改为 default 或给操作区新增面板，但这会改变既有阅读密度和表面层级，当前没有相应需求。共享组件只在局部修复无法满足契约、且有实际证据时做最小调整。

## Rationale

正文、目录和错误恢复已经有明确规则，本轮的主要缺口是容器之间怎样协作。逐处修复可以保留这些行为，并把 320px 下的内容压力交给换行和局部滚动。单独缩小全部内边距会减少阴影空间，重建布局壳又会扩大滚动和回归风险，均不符合这次收口的边界。

## Feature design

### Data, interfaces and state

本项是展示布局修复，没有新增实体、字段、迁移、业务 Action、HTTP 接口、持久化状态或运行配置。继续使用现有 `BlogList`、`ListItem`、`BlogListOperationBar`、`BlogMarkdown`、`CodeBlock`、`BlogReading`、`TOC`、`BlogOperationBar`、`AdjacentBlogsView`、`BlogStatusPanel` 和恢复组件接口。

| Surface | Existing input and output | Layout responsibility |
| --- | --- | --- |
| `/blog` | `getBlogList(1, 20, ...)` 的结果，URL 的 `content`、`orderBy` | 标题、上下文、操作区、文章集合与状态面板 |
| `/blog/[id]` | `getBlogById(id)` 的文章与互动状态 | 元信息、窄屏目录、正文、阅读操作与相邻导航 |
| 目录与进度 | 当前 BlogReading 实例及正文 DOM | 沿用 0013，只调整必要布局，不改计算与导航状态 |
| 相邻导航与恢复 | 现有查询结果、本地等待状态和恢复回调 | 现有状态自然换行，不改变请求或焦点恢复规则 |
| Blog 路由兜底 | 现有 loading、error、not found 入口 | 沿用 0014 的布局区域与恢复行为 |

公开读取继续匿名可用。新建、编辑及所有现有写操作继续由当前角色和 JWT Cookie 流程保护，样式调整不增加读取或写入权限。无新增日志、监控、密钥、外部素材或 SEO 行为。

### Spacing ownership and explicit exceptions

实际值来自 `src/app/globals.css`：default inset 为 `.75rem`（当前 12px），default gap 为 `.5rem`（当前 8px），compact inset 为 `.5rem`，compact gap 为 `.25rem`。组件引用变量，表中像素仅帮助理解，测量时以当前计算样式为准。

| Area | Padding and gap | Explicit exception and shadow owner |
| --- | --- | --- |
| Content 主区 | 横向使用 default inset，保留导航顶部和底部高度预算 | 顶底沿用 `--spacing-content-top`、`--spacing-content-bottom`，这是页面外壳偏移，不重复套面板 padding；主区为边缘面板和焦点提供留白 |
| 列表页面相邻区域 | default gap | 每个内容面板自行提供 default inset，外层不靠子元素 margin 排版 |
| 文章集合与 `#blog-container` | 组合包装层显式 `p-0`，default gap | 包装层不裁剪，边缘留白由 Content 主区提供；移除集合及子面板的常规外边距补偿 |
| 列表卡片 | 显式 `density="compact"`，保留既有平面表面 | 密集列表例外，卡片负责内部 Tag 与文字的留白；标题和元信息的纯布局包装显式 `p-0` |
| 详情文章面板 | default inset 与 default gap | 保留已有表面；标题、元信息与标签组合包装显式 `p-0` |
| 搜索、目录、状态、相邻导航面板 | default inset 与 default gap | 控件布局包装显式 `p-0`，面板负责内部按钮和 Tag 的阴影空间 |
| 阅读操作区 | 普通容器显式 default inset 与 default gap，允许换行 | 保留当前表面层级，由该容器提供按钮阴影空间；相邻距离归父级 |
| 作者与标签行 | 纯布局包装显式 `p-0`，使用 compact gap，允许换行 | 在 Blog 调用范围处理 Tag 内置 margin 与行间 gap 的叠加，阴影由所在面板的 inset 承担 |
| 正文、引用、表格、代码 | 沿用 0012 | 正文 compact 块间距、代码 margin 与内部 gap 不被父布局重置；表格和代码滚动包装的 `p-0` 继续显式保留 |
| BlogReading 及进度条包装 | 保留显式 `p-0` | 实例与进度轨道是结构或视觉包装，不是另一个内容面板，不增加裁剪边界 |

任何新增例外都需要在调用处表达，并在实施证据中说明由谁提供阴影空间。默认值不是给每个嵌套 div 自动加 padding。纯组合层采用上表的显式零值，避免窄屏反复消耗同一份内容宽度。

### Width, wrapping and scrolling

可收缩的 flex 或 grid 子项沿用 `min-width: 0`，内容最大宽度受所在区域限制。长标题、用户名、标签和上下文使用正常换行，必要时拆开无空格长串。列表和详情继续复用 Tag，在 Blog 调用范围处理其内部 `white-space: nowrap`，不修改其他页面 Tag 的默认展示。

搜索输入与操作按内容宽度换行，输入保持可编辑的宽度，不被按钮压成不可用区域。现有文字、按钮尺寸和 DOM 顺序保留，空间不足时可让输入或按钮独占一行。阅读操作仍使用现有回调，不顺带修复分享含义、按钮状态或交互反馈。

详情最大主栏宽度继续为 700px。布局判断读取 `.content-container` 的实际宽度，窄屏为 `width < 1088px`，桌面从 1088px 开始。桌面目录留在右侧，窄屏目录留在元信息之后、正文之前。保留现有外壳 1400px 规则，不新增按设备类型判断的分支。

桌面纵向阅读仍由 Content 主区承担，窄屏仍由页面承担。保留 `100dvh`、顶部导航和底部预算的协作，新增 padding 后不能让可滚动子区超过剩余高度。长目录的局部滚动继续由现有侧栏承担，不给整篇正文增加新的嵌套纵向滚动根。

代码和表格可横滚区域保留中文可访问名称、焦点和隐藏滚动条规则。只横滚这些区域时，正文纵向位置与进度不受直接影响。不得用 `body`、页面根或内容容器的 `overflow-x: hidden`、`clip` 掩盖布局超宽。

| --- | --- |

| 搜索词、排序、数量、等待和失败说明 | 当前规范化 URL、读取结果和 0014 的状态组件 |
| 相邻标题与链接 | 当前文章的相邻查询成功结果及既有方向规则 |

| 目录位置、当前项与进度 | 实际 Content 容器宽度及当前 BlogReading 实例，沿用 0013 |
| 横向溢出、可滚动范围与边界位置 | 浏览器实际 DOM 的 `scrollWidth`、`clientWidth`、`scrollLeft`、`scrollTop` 与矩形边界 |
| 阴影和焦点是否完整 | 对应主题、状态、滚动端点的截图与实际键盘检查，不能由元素矩形单独推断 |
| 压力样例 | 安全本地生成的固定标题、标签和 Markdown，真实路由使用现有测试作者创建的临时文章 |

### Verification and critical test scenarios

1. 基线与修复后使用相同样例。至少覆盖 320×568、390×844、768×900、1280×800、1440×900，四主题均检查真实列表和长文章。分别记录布局错误、已符合要求的区域和未能复现的候选点，验证 **AC-1**、**AC-3**、**AC-9**。
2. 压力样例包含连续 200 字符标题、连续 120 字符用户名、12 个标签（其中一个为连续 120 字符）、长搜索词、H1 至 H6 长目录标题、超长代码行、宽表格和保持比例的本地图片。测试边界不转化为业务输入长度限制。逐项检查文字完整、换行和所有操作可达，验证 **AC-3**、**AC-4**、**AC-5**。
3. 使用计算样式与边界测量核对上表的 inset、gap 和显式例外。滚到主区、侧栏及局部滚动区域的两端，检查首末面板、Tag、按钮阴影和键盘焦点。浏览器检查页面 `scrollWidth <= clientWidth + 1`，1px 只容纳舍入误差；另检查后代边界，防止裁剪导致该断言假通过，验证 **AC-2**、**AC-5**、**AC-6**。
4. 在同一真实长文章上，将 Content 容器实测宽度切到 1087px、1087.5px、1087.75px、1088px 和更宽，再反向切换。小数宽度通过测试容器尺寸设置后测量确认，不传给仅接受整数的视口 API。检查唯一活动目录、实际滚动根、展开后章节跳转与焦点，并确认进度仍按当前正文计算，验证 **AC-6**、**AC-7**。
5. 在 320px 和桌面覆盖列表各状态、空正文、404、页面失败与相邻导航失败，键盘完成恢复或清除操作，检查等待文字增长、状态替换及可达性。共享 loading 和 error 另外在新建、编辑入口做布局检查，正常编辑器流程不扩展，验证 **AC-4**、**AC-8**、**AC-9**。
6. 在 Album 现有 `blog-markdown`、`blog-reading`、`blog-status` 演示及 Blog 组件家族中维护实际变更的安全样例和来源映射。列表卡片若没有独立安全展示，可在该家族内补充纯本地样例，不导入生产查询或写入。Album 的宽度不能代替真实路由证据，验证 **AC-9**、**AC-10**。
7. 浏览器回归优先扩展现有 `e2e/blog-markdown.spec.ts`、`e2e/blog-reading.spec.ts`、`e2e/blog-status.spec.ts`，列表布局可增加专项场景。运行相关组件回归及 `pnpm lint`、`pnpm typecheck`、`pnpm build`、`pnpm test` 和本轮所需安全账号 Playwright。样例使用唯一标记，按现有保护核验本地数据库与账号，在清理阶段移除临时数据，验证 **AC-9**、**AC-10**。

源码检查不等于浏览器通过，矩形检查不等于阴影通过，旧报告也不等于本轮验证。减少动态效果沿用现有规则检查，不新增持续动画或额外运行时尺寸观察器。

## Build plan

采用项目 Tracer Bullet。每段都走真实数据读取、现有权限、共享组件、页面和浏览器观察，不先批量改完全部样式。

1. 记录基线后，先打通一条细线：使用安全测试作者的一篇压力文章，从真实列表卡片打开详情，修复首个已复现的宽度或间距问题，并在 320px 和桌面验证标题、标签、正文及现有操作。保持服务端读取与权限，满足 **AC-1**、**AC-2**、**AC-3**、**AC-4**、**AC-9**。
2. 沿同一阅读路径补齐代码、表格、目录和相邻导航，整理父级 gap、局部滚动、阴影与高度边界，验证断点往返及章节导航，满足 **AC-2**、**AC-3**、**AC-4**、**AC-5**、**AC-6**、**AC-7**。
3. 将同一布局契约应用到列表操作区和现有状态界面，确认共享兜底与必要共享组件的其他调用方，完成 Album 安全展示，满足 **AC-2**、**AC-3**、**AC-4**、**AC-6**、**AC-8**、**AC-9**、**AC-10**。
4. 补充实际缺陷的回归覆盖，完成四主题、宽度矩阵、键盘和减少动态效果检查及规定命令，汇总复现、修复和未验证证据，满足 **AC-1** 至 **AC-10**。

主要代码区域是 `src/app/blog/`、`src/components/BlogList/`、`src/components/Blog/`、`src/app/globals.css` 的 Blog 作用域，以及相应 Album 模块与测试。`Content`、Tag 和全局 UI 原语仅在证据表明必须调整时纳入，变更清单注明调用范围，避免将局部修复变成全站迁移。

## Consequences

**Positive**:

窄屏可完整阅读内容，布局取舍和间距例外可以复查。沿用现有组件与数据路径，改动能够逐段验证和回退。

**Negative / tradeoffs**:

完整标题和多标签会增加卡片高度，操作换行会增加工具区高度。保留 default 内边距后，320px 的正文可用宽度较小，长表格和代码仍需局部横滚。共享 Tag 的现有内层与 margin 需要在 Blog 范围处理，局部修复成本高于一次性全局重置。

**Neutral**:

无数据迁移和部署协调窗口，回退使用对应布局改动的版本回退。该规格的确认只确定设计，功能完成后才由实施流程推进到 Accepted。
