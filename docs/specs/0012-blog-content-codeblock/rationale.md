# 0012. 设计理由与项目来源

## Context at initial design

scope 28 来自 2026-10-20 的 Blog 设计审查。当前详情和编辑预览各维护一份 ReactMarkdown 映射，只有带语言标记的代码才进入 CodeBlock，且两处都传入 `test` 标题。正文样式仅给部分标题设置滚动偏移，没有独立的阅读排版规则。

现有 CodeBlock 位于 NotionBlock 文件中，使用固定 Dracula 配色并对代码执行 `trim()`，强制软换行。复制按钮没有中文操作名称或失败反馈。公开详情需要继续服务端输出，编辑预览则属于现有客户端编辑器。两处运行边界不同，但应对同一 Markdown 内容产生相同展示。

项目已有四主题、共享拟态组件、唯一全局 token 入口、Vitest 和 Playwright；本轮不能通过替换整个设计体系或更改文章存储来解决展示问题。当前工作区没有安装依赖，上一轮没有完成真实页面验证，因此本规格描述目标，不把源码推断写成已通过的运行结论。

## Options considered

### Option 1: 分别修补详情和预览

在两处现有映射中增加正文样式和高亮规则。（basis: 现有详情、MarkdownEditor 的小范围修补路径）

**Pros**:

1. 改动最集中，首次修补可以很快落地。
2. 不引入新的公开组件入口。

**Cons**:

1. 插件、代码识别和 fallback 继续由两处维护，预览一致性依赖人工同步。
2. 代码块仍与未在正式路径使用的 Notion 渲染集合耦合。

### Option 2: 共享正文渲染，逐处接入

抽出无业务依赖的正文与代码块，先接公开阅读，再接编辑预览和安全展示；保留现有依赖和兼容导出。（basis: scope 28 的共享规则目标，`src/AGENTS.md` 的组件复用约定，Tracer Bullet）

**Pros**:

1. 同一输入、插件和元素映射成为详情及预览的共同来源。
2. 可独立展示和测试代码块，不必让 Album 接触真实业务数据。
3. 无数据库变化，迁移可由一个组件接入变更回退。

**Cons**:

1. 增加两个组件入口，需要同时维护目录覆盖和消费方接入。
2. 必须小心划分服务端正文与客户端交互，避免把公开页面整体转为客户端。

### Option 3: 替换整个 Markdown 或高亮方案

改用新的编译或高亮依赖，同时重新建立正文展示。（basis: 当前 `package.json` 与锁文件中的既有解析和高亮依赖）

**Pros**:

1. 可以重新评估高亮包体积、服务端预处理和更丰富的代码元数据。
2. 新引擎可能提供现成的主题或扩展机制。

**Cons**:

1. 没有当前性能测量支持更换引擎，扩大依赖、语法兼容与构建验证范围。
2. 现有文章在边界语法上的输出可能变化，超出本次展示修复需要。

## Rationale

推荐 Option 2。需要消除的是正文展示规则分叉，现有依赖已覆盖 Markdown、GFM、标题 slug 和语法高亮。共享入口直接解决分叉，同时保留公开页面及作者编辑的原有数据路径。（basis: 现有组件盘点，scope 28，spec 0007）

用户最初选择标准阅读密度、默认横滚并提供换行开关、克制的语法配色。2026-10-20 的实际文章预览中，用户进一步确认紧凑正文、独立的代码按钮间距、默认图标按钮尺寸、Tag 语言标记和 `inset-sm` 代码面板。最终值统一记录在 [index.md 的排版与间距表](index.md#typography-and-spacing)，后续以该表和代码表面规则为准。不新增用户偏好存储、语言下载、代码执行或文件名解析。（basis: 本次设计对话与后续明确调整，单一职责与最小范围变更）

代码表面沿用背景和字体 token，语法专用颜色只覆盖必要分组。这样既能区分代码结构，又不会把语法误映射为成功、警告或危险状态。专用色集中加入现有主题区块，四主题比较无需依赖客户端主题判断。（basis: `design.md`，`src/app/globals.css`，spec 0007）

正文与预览接入放在本规格中，因为共享规则只有两处真实消费后才算完成；编辑器保存与提交的产品含义仍由 scope 33 决定。代码块的复制和换行区域也在此完成基本可访问性，避免新增控件立即欠下已知交互问题。（basis: scope 28、29、33，项目 Tracer Bullet）

## Palette evidence

方案按当前主题背景计算文字对比度，采用 sRGB 相对亮度公式。这里只是设计数值检查，实施后仍需读取实际 CSS 和浏览器计算样式复核，不代表四主题页面已经验收。

light 三组初步结果分别为 6.20、5.67、5.47；dark 为 8.72、9.94、6.34；sugar 为 6.52、5.46、4.69；warm 为 7.14、6.07、5.61。sugar 注释若直接沿用原有次要文字色，结果约 4.48，因此选择更深的专用注释色 `#68575a`，并纳入实施后的对比度检查。（basis: 当前四主题背景 token，本规格前景色方案）

## Independent cross check

2026-10-20 按用户选择，由 `gpt-6-astra` 只读复核规格，未修改文件或运行实现验证。复核未发现需要重新选择架构的缺口；指出现有编辑器换行转换和无行为“保存”按钮会造成验收歧义。主线程据此点明实际输入边界与现有“提交”路径，并补充末尾换行的行号示例。该复核不代表用户已经确认规格，也不代表实现通过验收。
