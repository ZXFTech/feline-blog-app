# 0016 的设计理由

## Context

现有 BlogEditor 只把编辑内容保存在 React 状态中，点击“提交”才调用 createBlog 或 updateBlogById。“保存”按钮没有处理函数，刷新不能恢复输入。提交成功先清空表单再导航，作者页权限与写 Action 不完全一致，保存失败、并发和迟到结果缺少统一控制。

预览已经使用共享 BlogMarkdown，但上游 onContentChange 会在换行前补两个空格，包括代码围栏内部。编辑器退出使用 Link 包裹 Button，窄屏预览以绝对定位覆盖输入，全屏的高度与焦点管理也需要收口。

你要求停止修改 1 秒后保存服务器私有草稿，只有提交才公开。已发布文章在编辑期间保留旧版，标题、正文与标签一同恢复，每篇文章只保留一份最新工作副本。你选择移除保存按钮、独立草稿页、原始 Markdown、冲突时保留本页并确认载入，以及确认删除且不影响已发布文章。

## Options considered

### Option 1: 在公开文章记录中增加草稿字段

同一 Blog 保存公开字段与一组私有字段，编辑器更新私有部分，提交时复制到公开部分。

优点是文章关联直接，已有记录和权限查询容易复用。代价是新文章的未发布状态需要参与所有公开查询过滤，详情返回和 include 稍有遗漏便可能暴露草稿，字段随两套快照重复。

### Option 2: 独立草稿记录，提交时更新公开文章

BlogDraft 保存工作副本，Blog 保留上次提交的公开版本。

优点是公开读取不需要引入草稿状态过滤，新文章草稿天然不进入公开列表与相邻导航。代价是新增私有读写、唯一关联、发布事务和并发控制。这是你选择的方案。

### Option 3: 以文章修订版本替代现有存储

每次保存生成独立版本，文章指向当前公开版本。

优点是可以保留历史、回滚和多版本比较。代价是重构公开读取与标签关系，持续写入和保留策略也更复杂，超过本轮一份最新工作副本的需要。

## Rationale

独立草稿最直接地满足“自动保存不公开”。现有公开列表、详情、API 和相邻导航都只读取 Blog，保留这些边界比让所有查询理解草稿状态更易验证。私有标签使用 JSONB 快照，是为了避免自动保存复用 upsertTags 时立即修改其他公开文章的共享标签颜色。

版本号与请求标识分别解决不同问题：版本号阻止另一设备的旧内容覆盖新草稿，请求标识识别网络超时后的同一次操作。客户端队列只能处理本页请求，不能替代数据库的原子版本检查。相较最后写入覆盖，冲突暂停更符合你要求的保留本页内容。

提交后保留最新工作副本和发布版本标记，能够直接判断是否仍有待发布草稿，并让再次编辑从完整副本开始。删除时清空私有文字并保留防重放元数据，避免迟到的首次保存重建已删除草稿。

独立模型复核发现，发布已提交但响应丢失后，另一设备可能删除草稿并清空文章关联，原请求便失去确认结果的来源。按你确认的修订，新增不含正文的 BlogPublishReceipt，随发布事务记录请求、作者、草稿版本和文章 ID。回执不随草稿或文章删除级联，原请求仅确认既有结果；文章现已删除时明确反馈。它记录操作结果，不保存内容历史，代价是保留少量额外元数据。

1 秒防抖与单请求队列使用既有 React 和 Server Action 即可，不需要新调度服务。相较逐字符写入，写入量可控；相较仅浏览器缓存，服务器草稿支持你选择的跨设备恢复。保存结果不明时先确认旧请求，再处理新快照，可以避免用一个请求标识表示两份正文。

界面沿用 design.md 和现有主题。桌面并排、窄屏切换来自你的选择，避免压缩正文与代码可用宽度。退出统一到我的草稿页，让保存后的工作有明确归处。正文渲染继续遵守 spec 0012，本轮仅移除它此前明确暂缓的编辑器上游转换。
